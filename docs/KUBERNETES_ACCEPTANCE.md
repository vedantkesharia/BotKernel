The core Helm deployment passed in **local kind v0.33.0, Kubernetes v1.36.1**, using one control-plane node. Docker Desktop's built-in Kubernetes remains disabled. EKS was unnecessary and no AWS calls or charges were incurred in this task.

The 32 mixed admission/replay/rejection POSTs had descriptive p50/p95/p99 of 135.243/258.035/289.763 ms, measured with a monotonic clock. These are response times, not completion times. ## Runtime defects found and fixed

1. **Unused checkpoint PVCs blocked Helm wait.** Agent-disabled installs created claims with no consumers under `WaitForFirstConsumer`. The chart now creates optional role claims only when agents are enabled. The interrupted test install was recovered using Helm rollback and upgrade. Two never-bound orphan claim objects were removed after verifying neither had a PV; data PVCs were preserved.
2. **Kafka health probes caused restarts.** JVM-based liveness/readiness commands inherited broker heap settings and timed out under CPU limits. Events show termination from liveness failures, not OOM. Startup/liveness now use TCP; readiness retains a real broker metadata command with a bounded 16-64 MiB JVM heap and longer interval/timeout. The corrected broker rolled out and remained Ready with zero container restarts during the subsequent observation. Earlier restart/503 evidence is retained.
3. Docker's cached multi-platform application image metadata prevented kind's default all-platform import. Saving/importing only `linux/amd64` resolved it; no image rebuild or ECR push was needed.

PostgreSQL restart temporarily disrupted dependent processes; one browser run recorded a readiness 503 while dependency restarts occurred. Later stable runs passed. No zero-downtime, HA, multi-node or general disaster-recovery claim follows.

## Resource observations and cleanup

Stopped nine historical BotKernel projects, preserving their containers and volumes: `botkernel-investigation-proof`, `botkernel-langgraph-validation`, `botkernel-observe`, `botkernel-trace-verification`, `botkernel-ui-review`, `botkernel-live`, `botkernel-bedrock-test`, `botkernel-bedrock-e2e`, `bk-final-regression`. These were completed proof/test environments; several had exited dependencies and thousands of background restart attempts. Eighteen successful, recreatable initializer containers were removed without volume removal. Active/uncertain projects were retained.

Available Docker memory rose to **3,185,992 KiB (~3.04 GiB)** before kind creation. The first current-engine sample, after the first six stops, was 1,401,480 KiB (~1.34 GiB), so the next three stopped projects reclaimed another ~1.70 GiB. The earlier 1.16 GiB figure is historical; a precise engine sample before the first six stops was not captured. The engine remains 12 virtual CPUs / 7.58 GiB. An age-filtered unused build-cache cleanup recovered **262.2 MB**; no image or volume pruning occurred. This is logical Docker cache reclamation, not a measured shrink of the Windows VHD; new cluster/container/PVC data also consumed disk. Disk reclamation is separate from RAM recovery. The node uses the same engine and is not a separate 7.58-GiB allocation.

One post-fix kubelet sample measured working sets: API 128.8 MiB, Kafka 316.3 MiB, PostgreSQL 59.6 MiB, publisher 53.9 MiB, worker 55.9 MiB, recovery 55.4 MiB, controller 54.1 MiB, Redis 9.7 MiB and dashboard 10.4 MiB. These are point samples, not peaks or requested limits; CPU samples and exact pod/image identities are in the evidence.

## Evidence and reproduction

[Sanitized evidence](../benchmarks/curated/kubernetes-2026-11-15/summary.json) includes raw request results, pending/final snapshots, worker/controller logs, restart timings, browser results and a SHA-256 manifest. The original 90 benchmark evidence hashes remain unchanged.

Use `scripts/kubernetes-runtime-check.py` only inside an explicitly dedicated Kubernetes API pod. `prepare` requires a fresh database and sets a constrained test quota; never run it against existing development or cloud data. Phases are documented in the script. It uses existing pod credentials without printing them, and refuses enabled cloud/model/action gates.

Current private access (from the repository root):

```powershell
kubectl --kubeconfig .local/kubernetes-completion/kubeconfig -n botkernel-acceptance get pods,svc,pvc
kubectl --kubeconfig .local/kubernetes-completion/kubeconfig -n botkernel-acceptance port-forward svc/dashboard 18080:8080 --address 127.0.0.1
```

The verified browser URL is `http://127.0.0.1:18080/app`. Use the dedicated private operator credential, never an AWS profile. If the existing tunnel owns the port, reuse it or stop only that tunnel before creating another.

To pause this owned local cluster without deleting its data, stop `botkernel-acceptance-control-plane`; start the same container to resume, then verify node and application readiness. Do not delete the kind cluster/container or PVCs without a retention decision: its local volumes live inside the node container. No always-on hosting is implied. Optional Kubernetes LangGraph agents and observability were not deployed in this acceptance; their static renders remain a separate claim.
